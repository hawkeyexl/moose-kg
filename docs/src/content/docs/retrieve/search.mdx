Retrieval needs two artifacts beside the graph: a lexical index, and optionally a vector sidecar.
This page builds both and explains what keeps them honest.

## Before you start

A built `kg/graph.ttl`. For real (non-mock) vectors you also need the optional peer dependency:

```sh
npm install @huggingface/transformers
```

## Build them

<Steps>

1. **Export the lexical index.**

   ```sh
   dockg export --format search
   ```

   ```
   Wrote 20 nodes to kg/search.json
   ```

   The index lives beside the graph rather than inside it. Prose belongs in neither — the index
   holds the short, searchable strings a node already carries (titles, labels), not document text.

2. **Compute vectors.**

   ```sh
   dockg embed
   ```

   ```
   Wrote 20 vectors (384-d, onnx-community/granite-embedding-small-english-r2-ONNX) to kg/vectors.bin
     20 embedded, 0 from cache
   ```

   For an offline or CI run with no model download, use deterministic hash vectors:

   ```sh
   dockg embed --model mock
   ```

3. **Query it.**

   ```sh
   dockg search "configuration" --limit 3 --mode lexical
   ```

   ```
   0.0164  https://example.com/kg/concept/configuration [skos:Concept] — Configuration
   0.0161  https://example.com/kg/doc/docs/configuration.md#configuration [dockg:Section] — Configuration
   0.0159  https://example.com/kg/doc/docs/configuration.md [dockg:Document] — Configuration Reference

   3 results (lexical)
   ```

   Drop `--mode lexical` and the same query runs `hybrid` when a sidecar is present: both legs
   score, and the fusion reorders. The trailing `(lexical)` / `(hybrid)` tells you which happened,
   so a run that quietly lost its vector leg is visible rather than merely worse.

</Steps>

## Embedding is local by contract

No API, no key, no spend, and **no corpus text leaves the machine**. That is a procurement fact as
much as a technical one, and it is worth having quotable.

Node and the browser **rank the same, though they do not compute the same floats**.
transformers.js uses a native ONNX runtime in Node and WASM in the browser, and it accepts
*different* `device` values on each, so there is no way to force one backend everywhere. Measured
on the default model, a query embedded in Node and the same query embedded in Chrome agree to
**cosine 0.999914**.

What dockg guarantees — and gates in CI against the real model in a real browser — is **decisive
ordering**: any two results clearly separated in score keep their relative order on both platforms.
Results within the noise of each other may swap, and in practice sometimes do, so do not treat the
tail of a result list as stable across platforms. dockg pins what is pinnable: single-threaded on
the WASM side, `q8` weights, one text per call.

## The three modes

| `--mode` | Runs | When |
|---|---|---|
| `hybrid` | Lexical and vector, fused | Default when a sidecar and embedder are both available |
| `lexical` | Lexical only | Always available; no sidecar needed |
| `vector` | Vector only | Diagnosing the vector leg in isolation |

A missing embedder **degrades to lexical** — unless you asked for `vector` or `hybrid` explicitly,
in which case it errors. Silent degradation is fine when you did not express a preference and wrong
when you did.

## Staleness is refused, not ranked

A vector sidecar built from a different corpus, model, dtype, or dimension count would still
produce numbers. Those numbers would be meaningless, and the results would look normal.

dockg refuses instead:

```
dockg: Vector index was built from a different search index — the corpus changed. Re-run `dockg embed`.
```

```
dockg: Not a dockg vector index: bad magic — is this the right file? — re-run `dockg embed`, or use `--mode lexical`.
```

Exit `2` in both cases.

<Aside type="caution" title="Rebuild order matters">
  The sidecar is keyed to the search index, which is keyed to the graph. Change the corpus and all
  three must be rebuilt in order:

  ```sh
  dockg build && dockg export --format search && dockg embed
  ```

  Skipping the last step gives you a refusal at query time rather than bad results, which is the
  intended failure — but it will fail your pipeline, so wire the three together.
</Aside>

## Do not commit the sidecar

`kg/vectors.bin` is gitignored by default. It is a binary, it is derived, and regenerating it
requires a model download — so it belongs in your deploy pipeline rather than your repository.
The graph and the search index are text and can reasonably be committed.
