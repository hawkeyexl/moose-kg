If you own a retrieval pipeline over documentation you did not write, this track is for you. It
puts a hard boundary in front of a ranker that cannot see one.

## What the runtime does, and where it stops

`dockg/runtime` takes a graph, a lexical index, and optionally a vector sidecar, and returns:

```ts
{ context, citations, trace }
```

Then it stops. **It never calls a model.** There is no prompt, no generation, and no opinion about
which LLM you use. It produces retrieval results and hands them back, so it drops into an
existing stack rather than competing with it.

It is also browser-native, with no `node:` imports and one small bundle. Embeddings sit behind a
separate entry point, so the query path never pulls in the model stack.

## The dependency, stated up front

**dockg's value here scales with metadata someone else has to add.**

A corpus with no `applies-to` values cannot be filtered by variant, no matter how good the runtime
is. If nobody has typed your documentation, dockg gives you sections, links, headings, and
citations. Useful, but not the boundary you came for.

<Aside type="caution" title="Measure before you integrate">
  Run `dockg stats` against the corpus and look at the coverage table. That number tells you how
  much lift to expect, and it is the number to take to the documentation team. Discovering it
  after you have built the integration is the expensive order.
</Aside>

## Why a typed edge rather than a better ranker

Two passages describing the same procedure for two different machines are nearly identical in
embedding space. Reranking does not separate them, because the wrong chunk genuinely is similar.
This is the failure mode that brought you here.

A typed edge separates them every time, with no threshold to tune. dockg is the filter you apply
before similarity is considered; your ranker still does the ranking.

## The artifact chain

Three files that must stay in sync:

| Artifact | Produced by | Purpose |
|---|---|---|
| `kg/graph.ttl` | `dockg build` | The typed nodes and edges |
| `kg/localizations.json` | `dockg export --format search` | Which localizations exist, and where |
| `kg/search.<lang>.json` | `dockg export --format search` | Lexical index, one per language |
| `kg/vectors.<lang>.bin` | `dockg embed` | Optional vector sidecar, one per language |

A mismatched model, dtype, dimension count, or corpus digest is **never ranked with**. A stale
sidecar produces plausible garbage, which is worse than an error, so the runtime refuses outright.
`dockg search` refuses too when you asked for the vector leg. Otherwise it warns and falls back
to lexical. A sidecar it merely found beside the graph should not turn a working search into a
failure.
