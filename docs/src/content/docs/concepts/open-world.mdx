---

A document with no `appliesTo` value has not told you it applies to nothing. It has told you
nothing at all.

That distinction sounds academic until it produces a wrong answer that looks right.

## The failure

Suppose you scope documentation by product variant, and you write the obvious query: *give me
every topic that applies to SP-X100.* You get results. They are plausible. The count is
reasonable. Nothing errors.

Now the topic that carries a critical interlock warning, and that nobody ever tagged, is missing
from that set — because it was never asserted to apply to anything.

Invert the query and it gets worse. *Give me every topic that does not apply to SP-X100*, written
as "topics with no matching `appliesTo`", returns every untagged topic in the corpus — including
the ones that do apply and were simply never annotated.

Both queries are silently wrong, in opposite directions, with no error to notice.

<Aside type="caution" title="This is the single most consequential idea on this site">
  Absence of an assertion is not an assertion of absence. Everything else about scoping follows
  from taking that seriously.
</Aside>

## Saying the stronger thing

When "this does not apply" is actually true, assert it. dockg mints negative predicates for
exactly this:

```md title="docs/interlock-reset.md"
---
kg:
  appliesTo:
    - SP-X100
  notApplicableTo:
    - SP-C40
---
```

That emits `dockg:notApplicableToVariant`, a real edge you can query. The same pattern exists for
subjects, as `notSoftwareSubject`.

Now the three states are distinguishable:

| Frontmatter | Meaning | Queryable as |
|---|---|---|
| `appliesTo: [SP-X100]` | Applies, asserted | `iirds:relates-to-product-variant` |
| `notApplicableTo: [SP-C40]` | Does not apply, asserted | `dockg:notApplicableToVariant` |
| neither | **Unknown** | absence of both |

**Query the negative edge, not the silence.** An interlock check that must exclude a variant has
to look for the explicit exclusion; anything else is inferring from a gap.

## Contradictions are caught

Asserting both directions for the same variant is a defect a human reviewer misses and an auditor
finds. `dockg check` catches it every build, via SHACL disjointness between `appliesTo` and
`notApplicableTo`, and it is a violation rather than a warning — so it exits 1 and fails your
gate.

## Unresolvable filters fail loudly

The same hazard shows up at query time. Filtering a traversal by a variant that does not exist in
the graph could reasonably return an empty set — and an empty set is indistinguishable from
"nothing matched", which is exactly the wrong answer for a filter meant to *exclude* something.

So dockg refuses instead:

```sh
dockg traverse "https://example.com/kg/doc/docs/setup.md" --variant SP-X999
```

```
dockg: Unknown product variant: SP-X999
```

Exit 2. A typo in a scope filter is an operational error, not a result.

## Use negative scope sparingly

Because the negative predicate is an assertion, it carries the same obligation as any other. Tag
what you actually know:

- **Do** assert non-applicability where it is a real, reviewed fact — safety, regulatory, and
  interlock content especially.
- **Do not** backfill `notApplicableTo` across a corpus for tidiness. You will be asserting things
  nobody checked, and the graph cannot tell a reviewed assertion from a bulk one.
- **Do** measure the gap instead. Low `appliesTo` coverage is a number, and
  [a number can be gated](/dockg/govern/coverage/).
