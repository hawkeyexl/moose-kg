Your pull request is red and a tool you may never have heard of is the reason. You are in the
right place, and you do not need to learn anything about knowledge graphs to get out of here.

dockg checks the **frontmatter** at the top of your Markdown file, the block between `---`
lines. It does not check your prose. So whatever failed, the fix is in that block.

## Is it even your fault?

Check the exit code, or just the shape of the message.

| What you see | Whose problem | What to do |
|---|---|---|
| A list of findings naming your file, exit `1` | Yours | Fix the frontmatter. Read on. |
| `dockg: <something>` in red, exit `2` | The pipeline | Hand it back to whoever owns CI. |

Exit `2` means dockg could not run properly at all: a missing file, an unreadable config, a
broken environment. Nothing you write in your page will fix it. Common ones:

```
dockg: No input files matched: docs/**/*.md (cwd: /repo/docs)
dockg: Graph not found: kg/graph.ttl — run `dockg build` first.
dockg: Localization manifest not found: kg/localizations.json — run `dockg export --format search` first.
```

<Aside type="tip" title="Say so when you hand it back">
  "dockg exited 2, which is an operational error rather than a content finding" saves a round
  trip. It is a real distinction the tool makes deliberately.
</Aside>

## Decode the error line

A validation failure looks like this:

```
✗ bad-kg.md
    /kg  must NOT have additional property 'bogus'  (line 3)  [/repo/schemas/docmeta-kg-1.0.0-proposal.1.json]
    /kg  must have property label when property alt-labels is present  (line 3)  [/repo/schemas/docmeta-kg-1.0.0-proposal.1.json]

1 file checked, 0 passed, 1 failed, 2 errors
```

| Part | What it tells you |
|---|---|
| `✗ bad-kg.md` | The file to open |
| `/kg` | Where in the frontmatter, here inside the `kg:` block |
| `must NOT have additional property 'bogus'` | The rule that fired |
| `(line 3)` | Where the `kg:` block starts, not necessarily the offending line |
| `[…docmeta-kg-1.0.0-proposal.1.json]` | The schema being enforced |

A graph-level finding from `dockg check` looks different. It names a concept rather than a file,
and lists the files responsible at the end:

```
violation: https://example.com/kg/concept/alpha skos:broader — skos:broader cycle through …/alpha, …/beta (…/alpha → …/beta) — a concept cannot be its own ancestor [docs/alpha.md, docs/beta.md]
```

The bracketed list at the end is where to go.

## Common failures

### An unknown key inside `kg:`

```
/kg  must NOT have additional property 'bogus'
```

The `kg` block only accepts a fixed set of keys, and a typo is an error rather than an ignored
line. Check the spelling against the [frontmatter reference](/dockg/reference/frontmatter/).

```diff lang="md" title="docs/guide.md"
  ---
  kg:
-   bogus: true
+   type: task
  ---
```

### A relationship without `label`

```
/kg  must have property label when property alt-labels is present
```

`alt-labels`, `broader`, `narrower`, and `related-concepts` all describe a concept, so there has to be a
concept to describe. Add the `label`, or remove the relationship.

```diff lang="md" title="docs/guide.md"
  ---
  kg:
+   label: Rate limiting
    alt-labels: [throttling]
  ---
```

### A value outside a controlled vocabulary

```
/kg/type  must be equal to one of the allowed values
```

`type`, `about-product-lifecycle`, and `about-product-aspect` accept fixed lists. They map onto a
published standard, so you cannot invent a value.

```diff lang="md" title="docs/guide.md"
  ---
  kg:
-   type: procedure
+   type: task
  ---
```

Permitted values: `task`, `concept`, `reference`, `learning`, `troubleshooting`, `form`.

### A `sections` key matching no heading

```
Broken section refs (1):
  docs/getting-started.md -> #missing-heading
```

Section metadata is keyed by heading slug, so renaming a heading orphans its entry. Update the key
to match the new heading, or delete it.

```diff lang="md" title="docs/getting-started.md"
  ---
  kg:
    sections:
-     install-the-cli:
+     installation:
        type: task
  ---

- ## Install the CLI
+ ## Installation
```

### A broken internal link

```
Broken internal links (1):
  docs/no-frontmatter.md -> missing.md
```

The link target does not exist on disk. Either fix the path, or check whether the link works on
the published site. If it does, the repo may be missing
[route mappings](/dockg/build/routes/), which is a config problem rather than yours.

A link to something that is not a document, such as an archive, a PDF, or an OpenAPI `.yaml`, never
appears here. dockg reads any explicit extension outside your `extensions` list as a static asset
your site serves, so there is nothing to fix and nothing is reported.

### Applicability that contradicts itself

```
violation: … dockg:notApplicableToVariant — applies-to and not-applicable-to share a value
```

A topic cannot both apply and not apply to the same product variant. Decide which is true and
delete the other.

### A concept cycle, or a `related`/`broader` conflict

```
violation: … skos:broader cycle through …/alpha, …/beta … [docs/alpha.md, docs/beta.md]
```

<Aside type="caution" title="This one may not be your page">
  A cycle is formed by several documents together, and the file you edited might be innocent. It
  may just be the one that closed the loop. The bracketed file list names every document involved.
  If they are not yours, this needs whoever owns the vocabulary rather than a quick fix.
</Aside>

### Two spellings of the same concept

```
warning: … concept carries multiple prefLabels (same slug, different spellings) — settle on one spelling
```

This is a **warning**, not a violation. It exits `0` and does not fail a build. If your job is
red, this is not why.

### A page-level key that derives nothing

```
dockg: test/fixtures/dd/harvest/guide.md: page key "applies_to" is not read by dockg and looks like "applies-to" — nothing was derived from it
```

The five page-level keys dockg reads are `type`, `concepts`, `applies-to`, `not-applicable-to`,
and `supersedes`. They are **not** schema-validated, because a page may legitimately carry any
other key its site generator or team needs. A misspelling is not an error. It is just a key dockg does not
read, and the fact you meant to declare is missing from the graph.

`dockg build` warns when a page key is one or two characters from one it does read. Fix the
spelling and rebuild. The same message appears for a page `type` value:

```
dockg: test/fixtures/dd/harvest/guide.md: page type "how to" maps to no iiRDS topic type and looks like "how-to" — no kg.type was derived
```

A page `type` with no iiRDS counterpart, say `blog-post` or `release-note`, derives nothing on purpose
and is not warned about. dockg references published iiRDS terms and never invents one.

This is a **warning**. It exits `0`, and nothing is derived either way. dockg reports what it did not
understand rather than guessing what you meant.

## Reproduce it locally

You can, and it is two commands:

```sh
npx @hawkeyexl/dockg validate
```

```sh
npx @hawkeyexl/dockg build && npx @hawkeyexl/dockg check
```

Run them from the repository root. Input globs resolve against your working directory, so
running from a subdirectory matches nothing.

If that does not reproduce what CI saw, your branch and CI probably disagree about the config.
Pushing a fix and re-running is usually faster than chasing that difference.
