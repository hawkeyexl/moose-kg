Someone requires that a given fraction of your documentation carries a given field, and today that
is tracked in a spreadsheet and discovered late. This page turns it into a number the build
enforces.

## What "covered" means

Coverage is computed over seven fields. Before agreeing to a threshold, know exactly what is being
counted:

| Field | A document counts as covered when |
|---|---|
| `title` | Frontmatter `title`, or a first H1 to fall back on |
| `description` | Frontmatter `description` |
| `creator` | Frontmatter `author` or `authors` |
| `created` | Frontmatter `date` or `created`, or a git-derived creation time |
| `modified` | Frontmatter `updated`, `lastmod`, or `modified`, or a git committer time |
| `subject` | At least one `tags`, `keywords`, or `kg.concepts` value |
| `label` | `kg.label` |

Note that `created` and `modified` depend on `provenance.git`. Turning git derivation off drops
both numbers for any document without explicit frontmatter dates — the corpus did not change, the
measurement did.

## Read the current number

```sh
dockg stats
```

```
Coverage:
  title        5/5  100.0%
  description  2/5  40.0%
  creator      1/5  20.0%
  created      1/5  20.0%
  modified     1/5  20.0%
  subject      3/5  60.0%
  label        1/5  20.0%
```

## Set thresholds per field

A single number across all seven fields is almost never what a real obligation looks like —
`title` at 100% and `label` at 40% is a coherent policy that one number cannot express.

```yaml title="dockg.config.yaml"
stats:
  coverageThreshold:
    title: 100
    description: 70
    label: 40
```

Unlisted fields are not gated. The per-field map is **config-only**; the
`--coverage-threshold` flag can only apply one number to every field, which is useful for a quick
check and not for encoding a policy.

<Aside type="tip" title="The first threshold's job is to hold the line">
  Set it just below current coverage, not at your goal. A gate pinned at the eventual target is red
  from day one, and a permanently red gate teaches the team to ignore it. Pinned just under today's
  number, it fails only on regression — and you raise it in the same pull request that improves the
  backlog.
</Aside>

## Gate on it

`stats` reports. `stats --check` gates.

```sh
dockg stats --check
```

Exits `1` when any threshold is breached, or when there are broken internal links or broken
section refs. Exits `0` otherwise.

Gating compares the raw ratio, not the rounded display value — so a field showing `70.0%` can
still fail a threshold of 70 if it is actually 69.96%.

<Aside type="caution" title="An empty graph is vacuously 100% covered">
  Coverage over zero documents passes every threshold. A misconfigured `inputs` glob therefore
  produces a green gate that checked nothing, which is worse than no gate at all.

  Assert the document count as well:

  ```sh
  dockg stats --format json > stats.json
  test "$(node -p "require('./stats.json').documents")" -gt 0
  ```
</Aside>

## Contradictions are a different gate

Coverage answers *is anything asserted?* It does not answer *is what is asserted consistent?* A
topic claiming both `applies-to: SP-X100` and `not-applicable-to: SP-X100` is fully covered and
self-contradictory.

That is caught by `dockg check`, via SHACL disjointness, and it is a violation rather than a
warning. Run both.

```sh
dockg check && dockg stats --check
```

## When the gap is structural

If current coverage is far below the obligation, a stricter threshold does not close it. See
[backfilling](/dockg/build/backfill/) and ratchet from there.
