dockg reads two kinds of frontmatter. **Page-level keys** are ordinary fields your site generator
probably already uses, read opportunistically and never validated. The **`kg` block** is dockg's
own, and it is validated against a published JSON Schema.

<Aside type="note" title="`kg:` is the frontmatter key; `dockg:` is the RDF prefix">
  You write `kg:` in Markdown. The graph uses the namespace prefix `dockg:`
  (`https://dockg.dev/ns#`). They are not the same thing and are easy to conflate.
</Aside>

## Page-level keys

Read by the `frontmatter` derive source. Aliases are listed in precedence order — the first one
present wins. **None of these are schema-validated**, so a misspelling is silently ignored rather
than reported.

| Frontmatter key | Aliases | Emits |
|---|---|---|
| `title` | falls back to the first H1 | `dcterms:title` |
| `description` | | `dcterms:description` |
| `author` | `authors` | `dcterms:creator` plus a `prov:wasAttributedTo` person node |
| `date` | `created` | `dcterms:created` (xsd:date) and `prov:generatedAtTime` |
| `updated` | `lastmod`, `modified` | `dcterms:modified` |
| `lang` | `language` | `dcterms:language` |
| `tags` | `keywords` | `dcterms:subject`, minting a `skos:Concept` per value |
| `generatedBy` | | `prov:wasGeneratedBy` a generation activity |

```md title="docs/getting-started.md"
---
title: Getting started
description: Install the SDK and make your first call.
authors:
  - Priya Raman
updated: 2026-04-11
tags:
  - onboarding
  - sdk
---
```

## The `kg` block

Validated against `schemas/frontmatter-0.8.json`, which ships in the npm package. Unknown keys
inside `kg` are an error.

### SKOS: what the document is about

| Key | Type | Emits |
|---|---|---|
| `prefLabel` | string | `foaf:primaryTopic` concept with `skos:prefLabel` |
| `altLabels` | string[] | `skos:altLabel` |
| `broader` | string[] | `skos:broader` |
| `narrower` | string[] | `skos:narrower` |
| `related` | string[] | `skos:related` |
| `subjects` | string[] | `dcterms:subject` (behaves like `tags`) |

<Aside type="caution" title="Four of these require `prefLabel`">
  `altLabels`, `broader`, `narrower`, and `related` all describe a concept, so the schema requires
  `prefLabel` to exist as the thing being described. Using one without it is a validation error —
  and `dockg fill` applies the same rule, silently dropping relationship proposals when no
  `prefLabel` exists or is being proposed alongside them.
</Aside>

Concept IRIs are minted from the slugified label, so two spellings of the same term converge on
one node. That is usually what you want; `dockg check` reports it as a **warning** so you can
settle on a spelling.

### iiRDS typing and applicability

Closed vocabularies bound to published iiRDS IRIs. dockg references those IRIs; it never vendors
or re-serializes the vocabulary.

| Key | Cardinality | Permitted values |
|---|---|---|
| `topicType` | single | `task`, `concept`, `reference`, `learning`, `troubleshooting`, `form` |
| `softwareLifecyclePhase` | list | `administration`, `customization`, `update`, `deployment`, `integration`, `deinstallation` |
| `softwareSubject` | list | `architecture`, `interface`, `system-requirement` |
| `appliesTo` | list | Free labels — each mints an `iirds:ProductVariant` |

### Negative scope

| Key | Cardinality | Emits |
|---|---|---|
| `notApplicableTo` | list | `dockg:notApplicableToVariant` |
| `notSoftwareSubject` | list | `dockg:notSoftwareSubject` — same three values as `softwareSubject` |

Both are disjoint from their positive counterparts: asserting the same value on both sides is a
SHACL **violation** and exits 1. See [open-world semantics](/dockg/concepts/open-world/) for why
these exist at all.

```md title="docs/interlock-reset.md"
---
kg:
  prefLabel: Interlock reset
  broader:
    - Safety procedures
  topicType: task
  appliesTo:
    - SP-X100
  notApplicableTo:
    - SP-C40
---
```

### `sections`

A map keyed by GitHub-style heading slug. Each value accepts `topicType`, `appliesTo`,
`softwareLifecyclePhase`, `softwareSubject`, `notApplicableTo`, `notSoftwareSubject`, and
`subjects`.

```md title="docs/maintenance.md"
---
kg:
  sections:
    reset-the-interlock:
      topicType: task
      appliesTo:
        - SP-X100
---
```

Two rules worth stating plainly:

- **Nothing is inherited.** A section does not pick up the document's `topicType` or `appliesTo`.
- **`prefLabel` and the SKOS hierarchy are not permitted** per section — they describe a concept,
  which is a document-level notion.

A key matching no heading emits `dockg:brokenSectionRef` and is reported by `dockg stats`.

### PROV-O

| Key | Type | Emits |
|---|---|---|
| `revisionOf` | string[] | `prov:wasRevisionOf` |
| `derivedFrom` | string[] | `prov:wasDerivedFrom`; unresolved targets become `dockg:brokenLink` |
| `generatedBy` | string | `prov:wasGeneratedBy`, associating the model as a `prov:SoftwareAgent` |
| `provenance` | object[] | Written by `dockg fill` — see below |

### `provenance` entries

`dockg fill` writes one entry per model, and **humans delete entries as they review them**. The
block is the outstanding-review queue rather than a permanent record.

| Field | Required | Notes |
|---|---|---|
| `generatedBy` | yes | The model that proposed the fields |
| `fields` | | Which of the twelve fillable fields it proposed |
| `confidence` | | Per-field score, 0–1, rounded to two decimals |

```md title="docs/api-keys.md"
---
kg:
  prefLabel: API keys
  provenance:
    - generatedBy: claude-opus-4-6
      fields:
        - prefLabel
        - topicType
      confidence:
        prefLabel: 0.92
        topicType: 0.81
---
```

## The twelve fillable fields

`fill.fields` restricts what `dockg fill` may ever propose. The full set: `prefLabel`,
`altLabels`, `broader`, `narrower`, `related`, `subjects`, `topicType`, `appliesTo`,
`softwareLifecyclePhase`, `softwareSubject`, `notApplicableTo`, `notSoftwareSubject`.

## Schema versions

`schemas/frontmatter-0.1.json` through `-0.8.json` are all published and all immutable. `0.8` is
the default. Point `validate.schemas` at an older version to pin, and expect evolution to arrive
as a new file rather than an edit to an existing one.

<Aside type="caution" title="Only YAML frontmatter can be written">
  `dockg fill` edits YAML frontmatter and preserves the body byte-for-byte. A TOML or JSON
  frontmatter fence is an operational error (exit 2) rather than a skipped file.
</Aside>
