Everything the CLI does is available as a function. Import the package root when you are building
moose-kg into a Node pipeline, a custom check, or another tool.

```ts
import { runBuild, runCheck, loadConfig } from "moose-kg";
```

<Aside type="note" title="Three entry points, three jobs">
  `moose-kg` is Node-side automation (this page).
  [`moose-kg/runtime`](/moose-kg/reference/runtime-api/) is the browser query surface.
  `moose-kg/embed` is the local model stack. The split is deliberate: the runtime never
  pulls in Node APIs, and a consumer who only queries never resolves the model stack.
</Aside>

## Commands as functions

Each takes an options object mirroring the CLI flags and returns a structured result instead of
printing. Paths resolve against `opts.cwd`, defaulting to `process.cwd()`.

| Function | CLI equivalent | Returns |
|---|---|---|
| `runBuild` | `moose-kg build` | Document and triple counts, the output path, warnings |
| `runCheck` | `moose-kg check` | Findings with severity, focus node, path, and responsible files |
| `runValidate` | `moose-kg validate` | Per-file results and a summary |
| `runFill` | `moose-kg fill` | Per-document status, fields written, cost |
| `runQuery` | `moose-kg query` | Matching quads |
| `runStats` | `moose-kg stats` | Counts, orphans, broken links, coverage |
| `runSearch` | `moose-kg search` | Ranked results with the trace |
| `runTraverse` | `moose-kg traverse` | Reached nodes and the trace |
| `runEmbed` | `moose-kg embed` | Vector count, dimensions, cache hits |
| `runExport` | `moose-kg export` | Node count and the output path |

Renderers for the pretty output are exported alongside them — `renderEmbed`, `renderSearch`,
`renderTraverse`, and their siblings — if you want the CLI's formatting without its process
handling.

```ts
import { runBuild, runCheck } from "moose-kg";

const built = await runBuild({ config: "moose.config.yaml" });
const report = await runCheck({ graph: built.outPath });

const violations = report.findings.filter((f) => f.severity === "violation");
if (violations.length) process.exitCode = 1;
```

<Aside type="caution" title="Errors are thrown, not exit codes">
  The functions throw `MooseKgError` where the CLI would exit `2`. The `0`/`1`/`2` mapping lives in
  `src/cli.ts`, not in these functions — so a wrapper decides for itself what a finding means. See
  [output & exit codes](/moose-kg/reference/output-and-exit-codes/).
</Aside>

## Configuration

| Export | Purpose |
|---|---|
| `loadConfig` | Discover, parse, and validate `moose.config.yaml`; returns a total resolved shape |
| `resolveBaseIri` | Normalize a base IRI the way `build` does |
| `COVERAGE_FIELDS`, `COVERAGE_FIELD_NAMES` | The seven fields coverage is measured over |

## Derivation and graph building

| Export | Purpose |
|---|---|
| `discoverFiles` | Apply `inputs`/`exclude` the way the CLI does |
| `analyzeDoc` | Parse one document into headings, links, images, code, frontmatter |
| `deriveGraph` | Turn analyzed documents into quads |
| `loadGraph`, `storeToQuads` | Read a `.ttl` back into a store |
| `collectGitHistory` | The git provenance source, injectable for tests |
| `frontmatterKind` | Detect YAML vs TOML vs JSON frontmatter |

## IRI minting

Stable IRIs are the graph's identity, so the minting functions are exported rather than reimplemented
by consumers.

| Export | Mints |
|---|---|
| `mintDocIri` | `{baseIri}doc/{repo-relative-path}` |
| `mintConceptIri` | A concept IRI from a slugified label |
| `mintAgentIri` | An agent IRI, segmented by PROV agent kind |
| `mintBuildActivityIri` | The build activity node |
| `conceptSlug`, `encodeSegment` | The slug and percent-encoding rules |

## Emitters

| Export | Produces |
|---|---|
| `emitTurtle` | Canonically sorted Turtle — the determinism contract |
| `emitJsonLd` | Deterministic JSON-LD |
| `emitRdfXml` | RDF/XML for the iiRDS package's `metadata.rdf` |
| `emitSearchIndex`, `buildSearchIndex` | The lexical index |
| `writeZip` | The deterministic zip used by the iiRDS export |

## Frontmatter editing

| Export | Purpose |
|---|---|
| `applyKgFields` | Write `kg` fields into YAML frontmatter, preserving the body byte-for-byte |
| `existingKgFields`, `existingProvenance` | Read what is already there |

## Vocabulary constants

`NS`, `PREFIXES`, `TOPIC_TYPE_IRIS`, `SOFTWARE_LIFECYCLE_IRIS`, `SOFTWARE_SUBJECT_IRIS`,
`MOOSE_KG_NOT_APPLICABLE_TO_VARIANT`, `MOOSE_KG_NOT_SOFTWARE_SUBJECT` — the same values the emitter uses.
See [emitted vocabulary](/moose-kg/reference/vocabulary/).

## Testing against the LLM path

`MockProvider` is re-exported so downstream tests can exercise `runFill` without a network call or a
credential. `makeProvider` and `resolveProviderIdentity` cover the config → provider mapping.

```ts
import { runFill, MockProvider } from "moose-kg";
```

<Aside type="note" title="The runtime exports are re-exported here too">
  `GraphIndex`, `traverse`, `assemble`, and the rest appear in both entry points, so Node-side code
  can query without a second import. The reverse is not true: nothing Node-specific leaks into
  `moose-kg/runtime`.
</Aside>
