This is the journey your taxonomy exists to serve, and the one where the expensive mistakes live.
A safety caution scoped to the wrong variant is not a metadata problem.

## Read this first

[Open-world semantics](/dockg/concepts/open-world/). Absence of `appliesTo` means **unknown**, not
"does not apply", and a scoping scheme built without taking that seriously fails silently in the
dangerous direction. It is not recoverable by better tagging afterwards.

## The four typing keys

Closed vocabularies bound to IRIs published by the iiRDS consortium. dockg references them; it
never vendors, re-serializes, or modifies the vocabulary.

| Key | Value | Emitted IRI |
|---|---|---|
| `topicType: task` | one of six | `iirds:GenericTask` |
| `topicType: concept` | | `iirds:GenericConcept` |
| `topicType: reference` | | `iirds:GenericReference` |
| `topicType: learning` | | `iirds:GenericLearning` |
| `topicType: troubleshooting` | | `iirds:GenericTroubleshooting` |
| `topicType: form` | | `iirds:GenericForm` |
| `softwareLifecyclePhase` | list of six | `iirdsSft:Administration`, `Customization`, `Update`, `Deployment`, `Integration`, `Deinstallation` |
| `softwareSubject` | list of three | `iirdsSft:Architecture`, `Interface`, `SystemRequirement` |
| `appliesTo` | free labels | Mints an `iirds:ProductVariant` per value, labelled with `dcterms:title` |

`topicType` is single-valued and emits `iirds:has-topic-type`. Lifecycle phases emit
`iirds:relates-to-product-lifecycle-phase`, subjects emit `iirds:has-subject`, and variants emit
`iirds:relates-to-product-variant`.

<Aside type="note" title="iiRDS is CC BY-ND, and that shapes the implementation">
  dockg only references published IRIs — the ones in the source are byte-verified against the
  consortium's published models. Nothing is copied into dockg's namespace, so no redistribution
  obligation reaches your users. Worth having quotable if a standards or legal reviewer asks.
</Aside>

## Say what a topic does not cover

```md title="docs/interlock-reset.md"
---
kg:
  prefLabel: Interlock reset
  topicType: task
  appliesTo:
    - SP-X100
  notApplicableTo:
    - SP-C40
---
```

`notApplicableTo` emits `dockg:notApplicableToVariant`; `notSoftwareSubject` does the same for
subjects. These are the only predicates dockg mints in its own namespace for scoping, and they
exist because the standard has no way to state the negative.

**Use them where the exclusion is a reviewed fact** — safety, regulatory, and interlock content
especially. **Do not backfill them across a corpus for tidiness**: the graph cannot distinguish a
reviewed assertion from a bulk one, and you will be asserting things nobody checked.

## Prove the scope, including what it excluded

<Steps>

1. **Traverse with a variant filter.**

   ```sh
   dockg traverse "https://docs.example.com/kg/doc/docs/maintenance.md" --variant SP-X100 --depth 2
   ```

   The variant can be given as an IRI, a `dcterms:title`, or a slug.

2. **Read the exclusions in the trace, not just the results.**

   The whole point of a scope filter is what it removed. A traversal that returns plausible
   results while silently dropping nothing is indistinguishable from an unfiltered one — check
   that the exclusions list is non-empty when you expect it to be.

3. **Confirm a bad filter fails rather than returning nothing.**

   ```sh
   dockg traverse "https://docs.example.com/kg/doc/docs/maintenance.md" --variant SP-X999
   ```

   ```
   dockg: Unknown product variant: SP-X999
   ```

   Exit `2`. An unresolvable filter would otherwise return exactly what it was meant to exclude,
   so dockg refuses instead of guessing.

</Steps>

## Contradictions fail the build

Asserting the same variant on both `appliesTo` and `notApplicableTo` is caught by SHACL
disjointness, as a **violation** — exit `1`.

```
violation: … dockg:notApplicableToVariant — appliesTo and notApplicableTo share a value
```

This is the defect a human reviewer does not catch and an auditor does.

## Document-level scope is a lie on long pages

If a page covers three variants, no document-level `appliesTo` is true for all of it. Push the
metadata down to the heading that owns the text — see
[section-level metadata](/dockg/model/sections/).
