---

A document that covers three product variants cannot be truthfully tagged with any one of them.
Section metadata is how you stop lying about two thirds of a page.

The principle behind it: [node granularity must match content
granularity](/dockg/concepts/granularity/).

## The map

Keyed by GitHub-style heading slug:

```md title="docs/maintenance.md"
---
title: Maintenance
kg:
  sections:
    reset-the-interlock:
      type: task
      applies-to:
        - SP-X100
    clean-the-optics:
      type: task
      applies-to:
        - SP-C40
      not-applicable-to:
        - SP-X100
---

## Reset the interlock

## Clean the optics
```

Each section node's IRI is the document's IRI plus the slug as a fragment, so it addresses an
exact span on disk:

```
https://docs.example.com/kg/doc/docs/maintenance.md#reset-the-interlock
```

Sections are derived whether or not you add metadata — the `sections` derive source emits a node
per heading with its level and sibling order regardless. The `kg.sections` map only adds meaning
to nodes that already exist.

## What a section may carry

| Permitted | Not permitted |
|---|---|
| `type` | `label` |
| `applies-to`, `not-applicable-to` | `alt-labels` |
| `about-product-lifecycle` | `broader`, `narrower`, `related-concepts` |
| `about-product-aspect`, `not-about-product-aspect` | |
| `concepts` | |

The SKOS keys are absent deliberately: `label` establishes what a *document* is primarily
about, and a concept hierarchy hanging off a heading is not a meaningful claim.

<Aside type="caution" title="Sections inherit nothing">
  A section does not pick up the document's `type` or `applies-to`. This surprises people and
  it is the right default — inherited applicability would silently recreate the document-level lie
  one level down, which is the exact problem sections exist to solve.

  If a section genuinely shares the document's scope, either state it again or leave the document
  tag to cover it. Do not expect the two to combine.
</Aside>

## Renamed headings are reported

Section keys are slugs of heading text, and heading text is prose that writers edit without
thinking about metadata. Rename a heading and its key matches nothing.

dockg reports it rather than ignoring it:

```
Broken section refs (1):
  docs/getting-started.md -> #missing-heading
```

That single behavior is what makes section metadata safe to rely on. Without it, section scoping
would be a system that degrades quietly every time somebody improves a heading — and the
degradation would be invisible until a scoped query returned the wrong set.

It is also gated: `dockg stats --check` exits `1` on a broken section ref, so a renamed heading
fails its own pull request.

## Verify a section resolves

```sh
dockg query -s "https://docs.example.com/kg/doc/docs/maintenance.md#reset-the-interlock"
```

```sh
dockg traverse "https://docs.example.com/kg/doc/docs/maintenance.md" --variant SP-X100 --depth 2
```

The second is the one that matters: a variant-scoped traversal over a section-annotated document
should return the sections that apply, not the whole document.

## Use it where scope actually varies

Section metadata costs more to author and more to review. A document that genuinely covers one
variant and one topic type should be tagged at document level; sections are for documents that are
not homogeneous.

Coverage numbers and the broken-section-ref count tell you where the document-level tagging is
already lying.

## Backfilling sections

Writing a `sections` block per page by hand does not scale past a small corpus, and
[`dockg stats`](/dockg/govern/coverage/) will tell you exactly how far behind you are — the section
coverage table starts at 0% on any corpus that has not adopted this.

`dockg fill --sections` (or `fill.sections: true`) asks the model for per-section metadata alongside
the document's, in the same call. It is **opt-in**, for two reasons: it costs more output per
document, and section metadata carries the same review obligation as anything else a model writes.

```sh
dockg fill --sections --dry-run
```

Two behaviors worth knowing before you run it:

- **A slug the model invents is dropped, not written.** Writing a block against a heading that does
  not exist would create exactly the broken section ref this page tells you to fix, so `fill`
  refuses. The report names the slug it discarded in a trailing
  `[no such section: …]`, and the JSON report carries it as `unknownSections`.

- **Preservation is per field, per section.** A value you set on one section is never overwritten
  without `--force`, and that does not stop the section beside it from being filled.

The confidence gate applies exactly as it does to document fields — a section field scored below
`fill.minConfidence` is reported and not written.
